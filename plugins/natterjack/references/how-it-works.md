# How the dashboard works

Read this when you need to change the engine, debug it, or explain a behavior. Everything here is the engine, in the workspace's engine folder (`<engine>/`: `natterjack/` by default, `dashboard/` in older workspaces, `.claude/dashboard/engine.json` `dir` says which); nothing in it is team-specific. The server finds the workspace by walking up from that folder to the nearest one with `.claude/dashboard/` (or `WORKSPACE_ROOT`), so the engine can sit at any depth (`tools/natterjack`).

## Shape

- **Server**: `<engine>/server/src/main.ts`, plain `node:http`, TypeScript run directly by Node ≥ 24 (type stripping; no server build, no npm dependencies). JSON API under `/api` (contract: `<engine>/shared/api.ts`), SSE for streaming run output, the built UI from `<engine>/dist/browser` (re-read from disk, so a UI rebuild needs no restart).
- **UI**: Angular (standalone components, signals, zoneless), no component library; global styles in `web/src/styles.scss`, pages under `web/src/app/pages/`. Built once on first start by `bin/dashboard.mjs`.
- **Config**: `server/src/config.ts` reads `.claude/dashboard/*.json` (cached by mtime). Each module reads its own file: `apps.ts`, `machine.ts` (+ `machine-catalog.ts`), `docs.ts` (+ `docs-providers/*`), `reference.ts`, `links.ts`, `deck.ts`, `issues/*`.
- **State**: `.claude/ledger/` (gitignored): `runs/<id>.json` + `.events.jsonl`, `apps/` job logs, `attachments/`, `settings.json`, tracker keys, `dashboard-token`, `dashboard.log`, `links.local.json`, `usage-snapshots.jsonl`.
- **Start/stop**: `bin/dashboard.mjs` (npm ci / ng build when stale, then a detached server; pid in the ledger).
- **Start at login**: `bin/dashboard.mjs autostart on|off|status` (`bin/autostart.mjs`) writes a per-user login item that runs `dashboard.mjs start`: a LaunchAgent on macOS (RunAtLoad, AbandonProcessGroup, no KeepAlive so `stop` stays stopped; it carries the PATH it was made with, since launchd's has neither `claude` nor nvm's node; output to `.claude/ledger/autostart.log`), a minimized Startup-folder shortcut on Windows (no admin, unlike an at-logon scheduled task). Named per workspace (folder name + hash), so several workspaces each get their own.
- **Restart from the page**: the sidebar footer shows the engine version and a restart link (not in hosted mode). POST `/api/restart` (`server/src/self-restart.ts`) hands `bin/dashboard.mjs restart` to a three-hop launcher: outside the process tree that stopping this server kills, and in a hidden console, so Windows opens no terminal windows for the commands it runs. Its output goes to `.claude/ledger/dashboard-restart.log`. The page then polls `/api/boot` until `startedAt` changes and reloads (`web/src/app/core/restart.ts`). Turns in flight are interrupted, as with any restart; the confirm says how many.

## Runs (the heart of it)

A run is a conversation; **each turn is a new `claude -p` process**:
`claude -p <prompt> --output-format stream-json --verbose --session-id <uuid> | --resume <uuid> --permission-mode <mode> --permission-prompts none --append-system-prompt <headlessRules() [+ outputsRule()] [+ PLAN_MODE_RULE]> [--model] [--effort] [--max-budget-usd] [--add-dir <attachments>]`

- **Questions**: headless Claude can't use AskUserQuestion, so `headlessRules()` (in `runs.ts`; other agents get `agentHeadlessRules()` in `agents/util.ts`) tells it to end the turn with `<<QUESTION>>{"questions":[…]}<</QUESTION>>`. The server strips it from the transcript, sets the run to `waiting`, and the page renders the options as buttons; the answer is the next turn.
- **Permissions**: `--permission-prompts none` denies anything that would prompt. Work that needs approvals belongs in a terminal ("Continue in terminal" hands the session to `claude --resume`).
- **Background work dies with the turn**: anything started with `run_in_background`, cron/loop schedules or monitors is killed when the process exits. The rules forbid it; the server flags runs that tried (`Background work stopped`). To leave apps running, the rules point runs at `bin/dashboard.mjs apps start` (by its absolute path; see Apps below), which has the dashboard start them detached. Hosted, or with no apps configured, they get the old advice (a workspace's own detached launcher, else the Apps page or a terminal).
- **Watches (loops)** replace loops that can't outlive a headless turn: Claude does one pass, then ends the turn with a `<<WATCH>>` block. The watch is stored on the run (`RunMeta.watch`), and `server/src/watches.ts` looks at it on a 30 s tick once it's due, only while the run is idle and done, and wakes the run with a reply (what happened, then the block's prompt). Three kinds:
  - **Pull requests** (`{"prs":["owner/repo#123"],"everyMinutes":5,"prompt":"…"}`): checked with `gh`. Wakes only on a new review or comment from someone else, failing checks, a review-decision change, the branch going behind or conflicting, or checks passing on an approved PR. Ends when every PR is merged or closed.
  - **Interval** (`{"every":"30m","prompt":"…","days":1}`, 10 minutes to 24 hours apart, for up to 7 days, and always at least two intervals): wakes every interval. This is what `/loop` becomes in a dashboard run.
  - **Check** (`{"command":"…","until":"change","everyMinutes":5,"prompt":"…"}`): the server runs the command with bash in the run's folder (Git Bash on Windows, never System32's WSL launcher; after 60 s the whole process tree is stopped) and wakes the run when its output or exit code changes, or, with `"until":"success"`, once when it exits 0 (then the watch ends). The first run only records. A command Claude wrote could have been planted by a prompt injection, so nothing runs until someone clicks **Approve and start** on the run page (`POST /api/runs/:id/watch-approve` with the watch's `startedAt` and `command` as shown, refused if a turn has replaced it since), unless deck.json `loops.allowCommands` matches it; the inbox lists checks waiting for approval.

  On a wake-up with nothing to do, Claude ends with `{"noop":true}` (counted as quiet wake-ups on the run page). Every kind ends after `days` (7 for PRs, 1 otherwise, by default), after 100 wake-ups, on `{"stop":true}`, or from the run page's Stop.
- **Routine proposals**: for work that should start fresh on a schedule, Claude ends the turn with `<<ROUTINE>>{"label":"…","prompt":"…","at":"09:00","days":"weekdays"}<</ROUTINE>>` (`RunMeta.routineProposal`). Nothing is scheduled until someone clicks **Create routine** on the run page (`POST /api/routines/from-run`). Routines run from `server/src/routines.ts` and are managed on the **Loops** page, which also lists every run with a watch on.
- **Blocks in answers**: `shared/blocks.ts` finds the question, watch and routine blocks for both the server and the run page. A marker inside code (Claude explaining how runs work) is just text, so an answer that mentions one isn't cut off there.
- **Queued messages**: while a turn runs, the composer queues what you type (`RunMeta.queued`; POST `queue`, `queue-edit`, `queue-remove`, `queue-send`, `queue-auto`), as typing ahead does in the CLI. Each one can be edited or removed until it's sent. When a turn ends as succeeded or failed, the whole queue goes out together as the next reply, under the same limits as a reply you send. If a limit blocks it, `queueBlocked` says why, and it's retried every 30 s. A question holds the queue unless **Auto-send** is on (`queueAutoSend`; the browser remembers your last choice for new queues). With it on, the queue goes out as the answer, led by a note (`QUEUED_OVER_QUESTION`): it isn't the answer, so Claude works on it first and then asks its question again. You can walk away without Claude deciding for you. A cancel or a restart always holds the queue, and the composer then offers Send now. Handing the run to a terminal clears the queue.
- **Plan mode** is a per-run switch applied each turn.
- **Limits**: concurrent runs, and new runs pause when `/usage` says the session or weekly window is past the threshold; optional per-run cap (`--max-budget-usd`). `total_cost_usd` in results is cumulative across resumed turns (don't sum it).
- **Environment**: runs get the user's environment minus Claude session markers. `ANTHROPIC_API_KEY` is also removed when this machine is signed in to a Claude subscription (so a stray key can't silently switch runs to per-token billing), and kept when it isn't (teams on an API key, Bedrock or Vertex). Sign-in state comes from `claude auth status` (`server/src/claude.ts`, cached a minute); runs refuse to start with a clear message while Claude is missing or signed out.
- **Attachments**: files you attach to a prompt or reply are uploaded to `<ledger>/attachments/_staged/`, move to `attachments/<runId>/` when sent, and their paths go in the prompt; that folder is passed as `--add-dir`. GET `/api/runs/<id>/files/<file>` serves them.
- **Files a run makes**: each run has an outputs folder, `attachments/<runId>/outputs/`, made before every turn. The run's rules name it (`outputsRule()` in `agents/util.ts`, for every agent), and the agent's process gets it as `DASHBOARD_OUTPUTS`, so a script can write there (`--output "$DASHBOARD_OUTPUTS/report.pdf"`) or the agent copies a file in. GET `/api/runs/<id>` lists what's in it (`outputs`: up to 200, subfolders flattened to `a/b.pdf`, dotfiles and links skipped), and the run page shows them in its **Files** tab (after Apps; only when there are files), re-read when a turn starts or ends. GET `/api/runs/<id>/outputs/<path>` serves one: only regular files inside the folder once links are resolved; PDFs and images inline, everything else (HTML and SVG included) as a download. Outputs are deleted with the run's attachments (Settings, **Keep attachments for**).
- **Changes tab**: each turn snapshots every repo's HEAD + `git stash create` + untracked list; the tab diffs against the first snapshot.
- Restarting the dashboard kills in-flight turns (marked `interrupted`; replying resumes). Apps it started keep running.
- **Sessions from a terminal** (`server/src/sessions.ts`): a Claude Code session started outside the dashboard (`claude` in a terminal, the desktop app, an IDE) in the workspace or one of its worktrees can become a run. Activity's **From terminal** lists them (GET `/api/sessions`), and **Open here** (POST `/api/sessions/adopt`) makes a run on the same session (`RunMeta.adoptedFrom`, tagged "from terminal"): its first prompt (not a `/clear` before it) is the run's prompt, the rest its events, and a reply resumes it. It keeps the session's permission mode, its latest as the terminal recorded it (a `permission-mode` line, or `permissionMode` on its prompts, not a dashboard turn's): plan mode as the run's plan switch, `bypassPermissions` as `auto`, and Claude Code's default mode (`manual`, once recorded as `default`) or none recorded as `manual`: a dashboard turn can't ask, so it reads and searches as it did in the terminal and anything that would have asked is refused. Never `dontAsk` unless the session was: it refuses everything not on the allow list, reading a file included. `manual` is only for these runs; runs aren't launched in it. With **Open terminal sessions here** on in Settings (`limits.adoptSessions`), sessions started since it was turned on (at most a day back; kept in `<ledger>/adopt-sessions.json`, so a restart skips none) become runs by themselves (`trigger: "terminal:auto"`). An older session picked up again with `claude --resume` isn't: open it with From terminal. Sessions are found in `~/.claude/projects` (or `CLAUDE_CONFIG_DIR`) by the folder name Claude Code gives a cwd, and kept only if their own `cwd` is inside the workspace. Scripted sessions (`claude -p`, the SDK), ones Claude never answered (only `/exit`, say), and ones over 64 MB are left out. What was said in an adopted run's terminal since is added to the run as events, under an "In the terminal" divider (every 30 s, and every few seconds while its page is open), so the run page, Remote control and Send to hosted all have it. Only what was written since the last read is read (`adoptedFrom.offset`), and only the terminal's lines: the dashboard's own turns are told apart by their entrypoint (`sdk-cli`), so what's typed there during one isn't lost. An answer given there clears a question the run asked here. While the terminal is still writing the session (the last 2 minutes), or running a tool (up to 30 minutes), a reply, Send to hosted and Continue in terminal are refused, so the conversation doesn't fork; a queued message waits and is retried. A terminal that's open but idle for longer can't be told from a closed one: exit it before replying from the dashboard, or the two copies of the conversation drift apart. An adopted run isn't under To review, Unrated, preset stats or standup until a turn has run from here. Not on a hosted dashboard.
- **Sessions from other folders**: Settings › **Sessions from other folders** adds folders outside the workspace (a project worked on before it, say) whose sessions From terminal lists too, grouped under the folder. It's personal (`<ledger>/session-folders.json`: `{ folders: [{ path, auto, autoSince }] }`, absolute folders outside the workspace, at most 20) and suggests the folders Claude Code was used in lately (GET `/api/sessions/folders`; `sessions.ts` `suggestFolders`, reading each project folder's path from one of its sessions). Each folder's **Open new ones by itself** (`auto`) does for it what `limits.adoptSessions` does for the workspace, from when it was turned on. Such a session can be:
  - **Opened here** (as above): it keeps working in its own folder, with that folder's CLAUDE.md and settings (`adoptedFrom.outside`). Remote control mirrors it; Send to hosted refuses it, since the hosted dashboard has only the workspace's repos.
  - **Moved here** (POST `/api/sessions/move`): `forkSession` copies it into the main workspace's project folder under a new session id (every line's `sessionId` rewritten, its subagents and tool results along), and `RunManager.moveIn` makes an ordinary run in the main workspace (`trigger: "terminal:moved"`, `movedFrom`, tagged "moved here"), told every turn that earlier paths are the old folder's and that its uncommitted changes didn't come along. It's a fork: the original carries on as it was in its terminal. A moved run can go to the hosted dashboard like any other.


## Apps

`apps.ts` runs `launch.cmd` (or the team's launcher) through a **two-hop launcher**: a detached `node -e` that starts the app non-detached with `windowsHide`, so the app gets a hidden console its children inherit (no terminal windows popping up on Windows) and survives dashboard restarts. "Up" = something answers on the app's port (IPv4 or IPv6). Each start/stop is a job with steps and a log.

`bin/dashboard.mjs apps <status|start|stop|restart|stop-all|setup>` (code in `bin/apps.mjs`) is the same thing from a terminal or a headless run: it sends the Apps page's POST `/api/apps/action` with the token from `<ledger>/dashboard-token`, then polls `/api/apps/jobs` and prints each step until the job ends (exit 0 or 1; on failure the error and `/api/apps/log` paths). The workspace is `--workspace <slug|path>` or the one in `/api/status` whose path holds the current folder (deepest wins, else main), so the dashboard's own slugs and discovery are used, never re-derived. It needs the dashboard running and won't start it; hosted mode refuses it.

## Workspaces

`workspaces.ts` finds them (ports file, `worktrees/*/.worktree.json`, and `git worktree list` on the root repo and each app's repo, cached 10s), their repos, and ports. A worktree's own port for an app comes from the ports file; with `worktrees.ports` set, `ensureSlot` allocates one on the first start, under `<portsFile>.lock`. `"fallback": "main"` is resolved when a command is launched: `{{port:<id>}}` names the worktree's instance if it answers on its port or is in the stack being started, else main's. A worktree stack starts (or reuses) main's instance of a fallback app it hasn't cloned; stopping that stack leaves main's alone.

## Get started

`onboarding.ts` builds the Get started page (`/setup`) from built-in steps (`BUILTIN_STEPS`: role, Claude, GitHub, the Atlassian secret and sign-in, the code, the machine, MCP servers) merged with the optional `onboarding.json`, each kept only where it applies and its `when` matches (machine.ts `whenMatches`, the same rules as machine checks). Every step's state is read from the check that already exists for it: `claude auth status`, the Machine report (the `gh` check, any `check` step, the required checks left over), the Atlassian sign-in, the repos on disk, the Connections page. Nothing is stored except per person, in `<ledger>/onboarding.json`: manual ticks and "I'll finish later". GET `/api/onboarding` evaluates it; `/api/boot`'s `onboarding` carries the last count (warmed at startup, re-evaluated after clone and download jobs, sign-ins and role changes), which the sidebar shows and which opens the page on first start. A pasted Atlassian client secret is written owner-only to `<ledger>/atlassian-client-secret` (POST `/api/onboarding/atlassian-secret`, local dashboards only, never echoed); `atlassian-auth.ts` reads it on each call, so Connect to Atlassian works without a restart.

## Installing it as an app; update check

The dashboard is a progressive web app: Chrome and Edge offer **Install** in the address bar (Safari: Share, Add to Dock or Add to Home Screen), on `localhost` and on a hosted dashboard's https address alike, and it then opens in its own window. `pwa.ts` serves `/manifest.webmanifest` per workspace (the name is `dashboard.title`, the colors `--brand-900` and `--paper` from `brand/theme.css`, the icon `brand/icon-*.png` or the SVG favicon), and `web/public/sw.js` is a service worker that caches nothing: it only shows a "can't reach the dashboard" page when a page load fails. index.html asks for the manifest with credentials, so a hosted dashboard's login proxy lets it through.

`update-check.ts` reads `https://asknatterjack.com/version.json` (`{ "version": "x.y.z", "notes": "<url>" }`, built from the site's `site.ts`) 15 seconds after start and every 12 hours; `GET /api/update` says whether it's newer than this engine, and the sidebar shows `v<x.y.z> available` (not to readers), which opens a run of `/natterjack:upgrade`. It's off with `dashboard.updateCheck: false` or `NATTERJACK_UPDATE_CHECK=0`, and always in hosted mode (its engine comes with the image). Publish a release to the site (deploy it with the new `version`) for workspaces to see it.

## Security

The server can start processes as the user, so no other origin may reach it. Hosted mode (`hosted.ts`, [hosting.md](hosting.md)) replaces the loopback and Host/Origin checks with its own: the login proxy's secret on every request, the public Host and Origin, and the signed-in email matching the container's owner. Locally it binds 127.0.0.1 only; the `Host` header must be `localhost`/`127.0.0.1` on its port (DNS rebinding); foreign `Origin`s get 403; every POST needs the per-install token from `/api/boot` (same-origin only). Install buttons and app commands come only from config files, never from the browser (it sends an id). Explore and brand/file serving refuse paths outside their roots and `.git`. Tracker keys never go to the browser.

## Pitfalls we've hit

- **After an engine update the page looks broken** (empty lists, missing brand): the old server process is serving the new UI. Restart it.
- **Don't restart the dashboard from a run inside it**: that kills the run. Ask the user to do it in a terminal.
- **`(event)="cond && doSomething()"` in an Angular template** returns `false` when `cond` is false, and a `false` from a handler calls `preventDefault`, which breaks every input inside. Handlers return nothing.
- **Injecting `Router` into a custom `TitleStrategy`** is a DI cycle (NG0200, blank page). Keep a reference to the last snapshot instead.
- **Windows**: `.cmd` shims (npm, az, composer) need a shell to run; `cmd.exe` mangles `^` and `$` in arguments, so only fall back to a shell when the plain exec fails. `jq` output has CRLF.
- **Never kill terminal processes** (WindowsTerminal, conhost) to stop something: kill the app's own process tree or whatever listens on its port.
- **A `.gitignore` that starts with `*`** (allow-list style) hides new top-level folders until `!folder/` and `!folder/**` are added; scaffold adds the dashboard's.
- **Node version**: the dashboard needs ≥ 24.22 (type stripping, Angular 22; 24.15 aborts natively on Windows during loopback HTTP). An older default Node shadowing a newer nvm one is common; `bin/dashboard.mjs` picks the nvm one.

## Searchable docs

`docs-providers/` reads external docs (Confluence first) with each person's own key: `/api/docs/external/*` for status, connect, search, a page, and search-all (global search, connected sources only). Page HTML is rendered through Angular's sanitizer, never bypassed. "Use <source>" on a run stores the sources on the run and appends each provider's `runNote` to the system prompt on every turn, which points Claude at that service's MCP tools; the dashboard's own key never reaches Claude.
